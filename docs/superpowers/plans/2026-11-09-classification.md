# Classification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each person has a line of work that shapes the builder, and each trail has a category and a city that the trail lists can search and filter by, on the website and in the app.

**Architecture:** The data lives in Supabase: `profiles.work`, `worlds.category`, and `worlds.city`. Two pure modules decide behaviour on the website. `web/src/lib/work.ts` maps line of work to visible features. `web/src/lib/place.ts` turns a point into a city via OpenStreetMap Nominatim. Every page reads those modules instead of deciding locally. The app reads the same columns through the existing RPCs and gains search, chips, a sign-up choice and a settings row.

**Tech Stack:** Postgres/Supabase (migrations applied with `pg` over `~/keys/supabase-db-url.txt`), Astro 7 static site + TypeScript, Playwright lab tests (`tests/lab/*.mjs`, `check()/done()` from `lib.mjs`), Node 22 `--experimental-strip-types --test` for pure-module tests, Unity 6 (UI generated by `Editor/AppUIBuilder.cs`, strings in `Services/AppStrings.cs`).

**Spec:** `docs/superpowers/specs/2026-11-09-classification-design.md`

## Global Constraints

- **Line of work values:** `broker`, `teacher`, `guide`, `other`. Null means "not asked yet" and is treated as `other`.
- **Category values:** `education`, `tourism`, `estate`, `other`.
- **Defaults per line of work:** broker → `estate`, teacher → `education`, guide → `tourism`, other → `other`.
- **Visible features:**

  | Line of work | Teams | Order choice | Questions + hints | Results tab | Team size / start time | One stop at a time |
  |---|---|---|---|---|---|---|
  | broker | no | no (any order) | no | no | no | no |
  | guide | no | yes | yes, without points | no | no | yes when in order |
  | teacher / other | yes | yes | yes | yes | yes | yes |

- **Hiding:** hidden means hidden completely, not tucked away. It's a preference, not a permission: the database never refuses a mode or step because of `work`.
- **Real-estate trails:** never show the "No teams · In order" line, to anyone. Show category · city instead.
- **City:** Nominatim reverse geocoding, `city` else `town` else `municipality`, never village or suburb. Store `{key, bg, en, lat, lng}`; `key` is the English name lower-cased and trimmed. Look it up again only while `city_auto` is true, and only when all stops are more than 5 km from `lat/lng`.
- **Sign-up choice:** required, nothing pre-selected. "Other" carries the hint "Всички възможности — и ако само ще вървите по маршрути." / "Every option — and for people who only walk trails."
- **Labels (BG / EN):**
  - Line of work: Брокер на недвижими имоти / Estate broker · Учител / Teacher · Екскурзовод / Tour guide · Друго / Other.
  - Categories: Образование / Education · Туризъм / Tourism · Недвижими имоти / Real estate · Друго / Other.
- **Free services only:** Nominatim without a key; send ≤ 1 request/s; the browser's Referer identifies us.
- **Existing accounts:** asked once (My trails on the website, sign-in in the app). Old trails keep every feature they already use.
- **Netlify credits:** push the website once per finished phase, not per task.

## Review Focus

1. **Never asked.** An account with `work = null` (existing users, guests turned real) sees the full builder, never an empty one. Owner: Task 3, test `featuresFor(null)` equals `featuresFor('other')`.
2. **Geocoding fails.** Nominatim is offline, rate-limited or returns no town. Saving a stop still works, the city stays empty, and the trail appears under "no city" in filters instead of vanishing. Owner: Task 4 (`cityAt` returns null and never throws) and Task 11 (a trail with null city is listed under All).
3. **Search across scripts.** "yambol", "Ямбол" and "ямбол" all find a Yambol trail; "ески" finds "Ески джамия". Owner: Task 3, test `matches()`.
4. **Hidden features on old trails.** A broker owning an old quiz trail sees the "this trail has questions" note; the questions stay in the database and in the app. Owner: Task 9 test.
5. **Guest upgrade.** A guest who becomes a real account in the app gets `work` saved; the update path doesn't fire the insert trigger. Owner: Task 14 test (DB row after upgrade).
